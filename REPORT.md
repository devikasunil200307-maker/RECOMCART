## 1. Introduction
An online shopping platform wants to recommend products that a customer is likely to purchase.
This project builds an end-to-end machine learning solution: data cleaning, feature engineering,
model training and evaluation, and a recommender that outputs the Top 5 products for an existing
or a new customer. A web app deploys the system.

## 2. Data
The dataset (`shopping_data.csv`) is synthetic, generated by `make_data.py` with a fixed random seed.

- 300 customers, 200 products, 5 categories (Books, Toys, Fashion, Electronics, Sports)
- Each customer has a hidden favourite category and budget; they view/cart/buy more of what they like and can afford
- 9,100 rows, with injected problems: about 100 duplicates, 50 missing prices and 10 invalid negative prices
- Overall purchase rate: 20.1% of rows

| Column | Description |
|---|---|
| customer_id, product_id | Identifiers |
| category, price | Product attributes |
| views, cart_adds, purchases | Interaction counts |
| previous_purchases | Customer's past purchases |

## 3. Data cleaning
| Problem | Treatment | Result |
|---|---|---|
| Duplicate rows | `drop_duplicates()` | 9,100 → 9,002 rows (some injected duplicates were no longer exact copies after other corruption) |
| Invalid prices (≤ 0) | Converted to missing | Handled with missing values |
| Missing prices | Filled with the same product's price from other rows; overall median as fallback | 0 missing prices remain |

## 4. Feature engineering
Target: `bought = 1` if `purchases > 0`, else 0.

Customer-level features: `cust_total_views`, `cust_total_cart`, `cust_avg_price`, `previous_purchases`.
Pair-level features: `price`, `price_ratio` (price ÷ customer's average price), `cust_cat_share`
(share of the customer's views that fall in the product's category). Category is one-hot encoded.

**Design decision, avoiding leakage:** the interaction's own `views` and `cart_adds` are excluded from the
inputs. A purchase cannot occur without a view and a cart add, so including them makes the problem
trivial and leaves the model unable to score products a customer has never seen, or new customers.
An early version that used them gave near-zero probabilities for every unseen product.

## 5. Model
`RandomForestClassifier` with 200 trees, trained on 80% of the data (7,201 rows) and tested on 20%
(1,801 rows), with a stratified split so both parts keep the same purchase rate.
A Random Forest handles mixed numeric features, needs no scaling, and is robust on small tabular data.

## 6. Evaluation
Decision threshold 0.3 (lowered from 0.5 because only ~20% of rows are purchases).

|  | Predicted no | Predicted yes |
|---|---|---|
| **Actual no** | 1,146 | 296 |
| **Actual yes** | 193 | 166 |

| Metric | Value |
|---|---|
| Accuracy | 0.782 |
| Accuracy of "always no" baseline | 0.801 |
| Precision | 0.359 |
| Recall | 0.462 |
| F1 | 0.404 |
| ROC-AUC | 0.704 |

**Interpretation.** Accuracy is lower than the trivial baseline, so it is not a useful metric on this
imbalanced data. ROC-AUC of 0.70 (0.50 = random) shows the model ranks buyers above non-buyers
meaningfully better than chance, which is what ranking recommendations requires. The model is
moderate, not excellent, partly because purchases in the data are generated randomly and cannot be
predicted perfectly.

Threshold trade-off: a higher threshold raises precision and lowers recall; a lower threshold does the opposite.

## 7. Recommendation engine
For an **existing customer**: take all products, remove ones already bought, build the customer's
features for each product, predict purchase probability, sort descending, show the Top 5.

For a **new customer**: the user supplies favourite categories, typical budget and previous purchases.
Category share is split evenly across the favourites, average price is the budget, and unknown activity
levels use the median customer. The same ranking step is applied.

Example (new customer, likes Books, budget 40): Top 5 are all Books priced mostly under 40,
with probabilities between about 47% and 59%. The high percentages reflect that the Top 5 are
the best of about 190 candidates.

## 8. Deployment
`app.py` is a Streamlit app with two tabs (existing customer by ID, new customer by details), deployed on
Streamlit Community Cloud from this repository.

## 9. Limitations and future work
- Synthetic data; real-world performance is unknown.
- Only ROC-AUC/F1 reported; add Precision@5 and compare with a "most popular products" baseline.
- Probabilities are not calibrated.
- Try gradient boosting, tune hyper-parameters, and add collaborative filtering.
- Cold-start handling for a new customer is based on stated preferences only.
